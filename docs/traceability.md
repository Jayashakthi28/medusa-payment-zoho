- **Scope:** Repository implementation and documentation as checked in on this date

  user-facing explanation. If a cell says "none", treat it as a gap, not as approval.

## 3. Remaining verification gaps

These are deliberate, documented limits of the current release. Everything else in the
matrix is verified by the local gate.

1. **No live Zoho sandbox in CI.** There are no merchant credentials in the repository.
   `scripts/smoke.mjs` is the gated live check; all automated tests use documented
   fixtures and an injected fake client.
2. **No full Medusa application boot fixture.** The unit suite imports the real
   `ModuleProvider`, verifies `pp_zoho_zoho` identity, and calls the provider directly.
   The webhook route itself is Medusa-owned and documented; it is not booted with
   PostgreSQL/Redis in this repository.
3. **Node 20 is declared but not exercised in CI.** CI runs Node 22 and 24 because the
   current Medusa 2.22 toolchain requires Node 22.22+. The package runtime target is
   Node 20 for older Medusa 2.17.2+ lines.
4. **No real-browser E2E.** The widget helper is exercised in jsdom with a stubbed
   `window.ZPayments`; the Zoho CDN and real widget iframe are not loaded in CI.
5. **Live refund settlement is manual.** The refund request, response mapping, and
   replay guard are unit-tested; bank settlement timing is Zoho/network dependent.

## 4. How to update this document

When a public behaviour changes:

1. Add a new ADR; do not rewrite an accepted one. Link it from the matrix row.
2. Update the source and test columns with the real file paths.
3. Update the user-facing document. Flows belong in architecture or the storefront
   guides, limitations in compatibility, verification in testing, and merchant setup in
   the integration listing.
4. Re-run `pnpm test:coverage`. A new branch without a test fails the gate.
5. If a gap in Section 3 is fixed, remove or amend the entry in the same change.
